## 1. Executive summary and architecture

The lexer reads a `.rice` source file and groups its characters into tokens:
keywords, identifiers, literals, operators, delimiters, comments, and invalid
tokens. It operates purely as a lexical scanner; it does **not** parse statements, build an abstract syntax tree, or validate runtime types.

```text
  .rice source file
         |
         v
  lexer_read_source()
  Validate file extension, regular file status, and character encoding
         |
         v
  lexer_scan()
  Track position and recognize each lexical element
      |                    |
      | words/symbols      | literals/comments/errors
      v                    v
  dfa_step()          lexer_scan() branches
  dfa_find_accept()   Bound and classify the lexeme
      |                    |
      +---------+----------+
                v
    Temporary token and trace streams
                |
                v
    main() assembles "Symbol Table"
```

### Architectural pillars

1. **Self-contained single-file architecture.** All token enumerations, DFA transition logic, character classification routines, input validation, scanning loops, and file reporting reside in [`lexer.c`](./lexer.c). This simplifies compilation and eliminates header synchronization issues.
2. **Explicit input validation.** `lexer_read_source()` requires a lowercase `.rice` extension and a regular file. It accepts printable ASCII, tab/newline/carriage-return whitespace, and supported two-byte UTF-8 sequences for Filipino letters (`ñ` / `Ñ`). If validation fails, error messages are printed to stderr and written directly to `Symbol Table`.
3. **Deterministic Finite Automaton (DFA) for words and symbols.** The current state plus next character uniquely determines the next state. Word prefixes are encoded as explicit named states (`WORD_L`, `WORD_LE`, etc.); symbol states handle punctuation and multi-character operators (`==`, `!=`, `>=`, `<=`, `&&`, `||`).
4. **Accepting-state metadata table.** A constant table (`accepting_states`) maps accepting DFA states directly to `TokenKind` enumerations and category classifications (e.g. `KEYWORD`, `BUILT_IN_METHOD`, `TRANSACTION_VERB`). The lexer does not rely on post-scan string comparisons (`strcmp`).
5. **Separate token and trace streams.** The scanner writes recognized token rows and character-by-character DFA transition logs to separate temporary streams (`tmpfile()`). `main()` combines them into the final formatted `Symbol Table` report.
6. **Explicit diagnostic and error tracking.** Lexical errors are printed to stderr with exact line and column coordinates, emitted as `INVALID` entries in the token table, and reflected in a non-zero exit code (`EXIT_FAILURE`).

> **Naming clarification:** `Symbol Table` is the output filename. The file is a token-and-trace report generated by the lexical analyzer, not a compiler symbol table of variables and runtime scopes.

### Project file map

| File | Responsibility |
|---|---|
| [`lexer.c`](./lexer.c) | Consolidated self-contained C program: token definitions, DFA state transitions, source reading, lexical scanning engine, symbol table generation, and entry point (`main`). |

## 2. Source code organization and function inventory

[`lexer.c`](./lexer.c) is divided into 6 distinct, structured sections:

```text
Section 1: TOKEN DEFINITIONS       - TokenKind enum & AcceptingState struct
Section 2: DFA DECLARATIONS        - Character classes, states & function declarations
Section 3: LEXER DECLARATIONS      - Declarations for lexer_read_source & lexer_scan
Section 4: DFA IMPLEMENTATION      - Word & symbol transitions, acceptance table, formatting
Section 5: LEXER IMPLEMENTATION    - Input reading, memory buffers, character scanning loop
```

## 3. Data and state lifecycle

### Input buffer lifecycle

```text
path argument (argv[1])
     |
     v
valid_source_extension()
     |-- (invalid) -> prints error to stderr & "Symbol Table", exits EXIT_FAILURE
     v
stat() & S_ISREG()
     |-- (invalid) -> prints error to stderr & "Symbol Table", exits EXIT_FAILURE
     v
fopen() in "rb" mode
     |
     v
fgetc() byte loop:
     |-- UTF-8 0xC3 0xB1 / 0xC3 0x91 -> append both bytes
     |-- Valid ASCII & whitespace    -> append_char()
     |-- Unsupported character       -> READ_FAIL, clean up, write to "Symbol Table", exit
     v
Dynamically allocated buffer (starts at 64 bytes, doubles on demand)
     |
     v
lexer_scan() processes buffer
     |
     v
free(source) in main()
```

- **Clean error output on input failure:** If file validation fails (bad extension, missing file, or unsupported bytes), the lexer writes the plain diagnostic string directly to `Symbol Table` and exits immediately with `EXIT_FAILURE`.
- **Accurate column tracking:** UTF-8 sequences for `ñ`/`Ñ` consume 2 bytes in memory but advance the displayed column counter by only 1.

### Scanner-local state

The scanner does not rely on global cursors. `lexer_scan()` maintains all scanning state in local variables:

| Variable | Type | Meaning |
|---|---|---|
| `pos` | `size_t` | Zero-based byte offset into the source buffer. |
| `line` | `size_t` | One-based source line counter (incremented on `\n`). |
| `column` | `size_t` | One-based visual column counter (reset to 1 on `\n`). |
| `token_line`, `token_column` | `size_t` | Starting coordinates captured at the beginning of each lexeme. |
| `errors` | `int` | Running count of lexical errors encountered. |

### Output lifecycle

`main()` manages two temporary streams created with `tmpfile()`:

1. `token_table`: Stores the formatted rows of tokens (e.g. `TOKEN_KW_BUO | BUO`, `LINE_COMMENT`, `INVALID`).
2. `scan_log`: Stores the step-by-step trace of scanned characters, character classes, DFA state transitions, and `ACCEPT`/`PASS`/`REJECT` records.

Once scanning finishes:
1. `main()` opens `Symbol Table` for writing.
2. It writes the token table headers and copies `token_table` using `copy_stream()`.
3. It writes the trace section divider and headers, then copies `scan_log`.
4. Both temporary files are closed (which automatically deletes them from disk).
5. `Symbol Table` is closed, and `main()` exits with `EXIT_SUCCESS` (0) or `EXIT_FAILURE` (1).

## 4. Operational trace cases

All transitions execute through `dfa_step()` and local scanner branches in [`lexer.c`](./lexer.c).

### Trace case 1 — Reading and reporting a source file

**Execution**

```powershell
.\lexer.exe .\program.rice
```

1. `main` verifies that `argc == 2`.
2. `valid_source_extension` confirms `.rice`.
3. `lexer_read_source` validates regular-file attributes and character sets.
4. `scan_log` and `token_table` are initialized via `tmpfile()`.
5. `lexer_scan` consumes the buffer and records transitions.
6. `main` writes headers and merges streams into `Symbol Table`.
7. `free(source)` releases the buffer. Process exits 0 if no lexical errors occurred.

### Trace case 2 — Reserved word `BUO` versus an identifier

**Input**

```rice
BUO BUOLALA
```

For `BUO`, the word transitions are:

| Character | State transition | Meaning |
|---|---|---|
| `B` | `q0 -> q12` (`WORD_B`) | Initial transition from `STATE_START`. |
| `U` | `q12 -> q13` (`WORD_BU`) | Matches prefix for `BUO`. |
| `O` | `q13 -> q14` (`WORD_BUO`) | Reaches accepting keyword state. |

`dfa_find_accept(q14)` returns `TOKEN_KIND_KW_BUO` (`KEYWORD`).

When scanning `BUOLALA`, the scanner processes `B`, `U`, `O` into state `q14`. When the next character `L` arrives:
- `WORD_BUO` cannot transition on `L`, so `dfa_step_word` returns `STATE_IDENTIFIER` (`q900`).
- The remaining letters `A`, `L`, `A` remain in `q900`.
- At the end of the word, `dfa_find_accept(q900)` returns `TOKEN_KIND_IDENTIFIER`.

### Trace case 3 — Numeric literal and decimal lookahead

**Input**

```rice
120.00.
```

1. Initial digits `1`, `2`, `0` transition from `STATE_START` (`q0`) to `STATE_INTEGER` (`q901`).
2. When the first `.` is encountered, the scanner inspects the lookahead byte (`source[pos + 1]`). Because it is a digit (`0`), the dot is consumed and transitions to `STATE_DECIMAL` (`q902`).
3. Digits `0`, `0` are consumed in `q902`. The accepted token is `TOKEN_NUMERO_LITERAL`.
4. When the trailing `.` is scanned on the next iteration, lookahead reveals no following digit. It is therefore recognized independently as `TOKEN_TERMINATOR` (`q920`).

### Trace case 4 — Single and compound symbols

**Input**

```rice
= == && :
```

For each symbol, `lexer_scan` tests `dfa_step(STATE_START, c)`. If a second character exists, it tests a compound transition:

| Lexeme | State path | Resulting token |
|---|---|---|
| `=` | `q0 -> q934` | `TOKEN_ASSIGNMENT` |
| `==` | `q0 -> q934 -> q935` | `TOKEN_REL_EQ` |
| `&&` | `q0 -> q942 -> q943` | `TOKEN_LOGIC_AND` |
| `:` | `q0 -> q922` | `TOKEN_ACCESSOR` |

A single `&` reaches non-accepting state `q942`. The scanner detects no acceptance, rejects the symbol, and logs a lexical error.

### Trace case 5 — UTF-8 `ñ` in an identifier

When `ñ` (`0xC3 0xB1`) or `Ñ` (`0xC3 0x91`) appears in an identifier (e.g. `Kañin`):

1. `dfa_is_filipino_letter()` recognizes the two-byte UTF-8 sequence.
2. The scanner transitions to `STATE_IDENTIFIER` (`q900`).
3. `pos` advances by 2 bytes, but `column` advances by 1.
4. The transition trace logs the character as `[ñ]`.

### Trace case 6 — Lexical errors and recovery

- **Leading underscore:** `_presyo` transitions to `STATE_ERROR` (`q905`). An error diagnostic is reported: `Identifier must not begin with an underscore: '_presyo'`.
- **Digit-leading identifier:** `123user` consumes the alphanumeric span and logs: `Identifier must not begin with a digit: '123user'`.
- **Unrecognized character:** `~` triggers `STATE_ERROR` from `STATE_START`. It logs `Unrecognized character '~' (ASCII 126)` and advances past it.
- **Unterminated string:** `"Adobo` reaches newline without closing `"`. It logs `Unterminated string literal.`

## 5. Token and DFA reference

### General and literal states

| State constant | Value | Role |
|---|---:|---|
| `STATE_START` | `0` | Start state. |
| `STATE_IDENTIFIER` | `900` | Identifier state. |
| `STATE_INTEGER` | `901` | Integer literal (`TOKEN_BUO_LITERAL`). |
| `STATE_DECIMAL` | `902` | Decimal literal (`TOKEN_NUMERO_LITERAL`). |
| `STATE_STRING` | `903` | String body scanning state. |
| `STATE_COMMENT` | `904` | Line comment scanning state (`@...`). |
| `STATE_ERROR` | `905` | Error transition state. |
| `STATE_CHAR` | `906` | Character literal body state. |
| `STATE_STRING_END` | `907` | Accepting state for strings. |
| `STATE_CHAR_END` | `908` | Accepting state for character literals. |

### Word and symbol states

- **Keywords and reserved words:** States `WORD_L` (`1`) through `WORD_ngani` (`174`).
- **Symbols and operators:** States `SYMBOL_DOT` (`920`) through `SYMBOL_PIPE_PIPE` (`945`).

### Accepting state mapping (`accepting_states`)

`accepting_states` in [`lexer.c`](./lexer.c) maps accepting states to their tokens:
- **Keywords (11):** `BUO`, `HINTO`, `KUNDI`, `KUNDISYON`, `KUNG`, `LETRA`, `NUMERO`, `SALITA`, `TULOY`, `ULIT`, `WALA`.
- **Reserved words (20):** `TAMA`, `MALI`, `KATUMBAS`, `ULAM`, `RESIBO`, `ORDER`, `LUTO`, `HAIN`, `BAYAD`, `ilagay`, `meron`, `kumuha`, `dagdag`, `bawas`, `kalkula`, `diskwento`, `bayaran`, `ilimbag`, `linisin`, `hatian`.
- **Noise words (11):** `po`, `na`, `lang`, `at`, `nang`, `ng`, `ang`, `ay`, `nito`, `opo`, `ngani`.
- **Operators & delimiters:** `+`, `-`, `*`, `/`, `%`, `^`, `\`, `=`, `==`, `!=`, `>`, `>=`, `<`, `<=`, `!`, `&&`, `||`, `.`, `,`, `:`, `(`, `)`, `{`, `}`.

## 6. Build, run, and verify

### Compilation

Because the implementation is unified into a single file, only [`lexer.c`](./lexer.c) needs to be compiled:

**Windows (GCC / MinGW / MSYS2):**

```powershell
gcc -std=c11 -Wall -Wextra -pedantic lexer.c -o lexer.exe
```

**macOS / Linux (Clang / GCC):**

```bash
clang -std=c11 -Wall -Wextra -pedantic lexer.c -o lexer
```

### Running the examples

**1. Normal valid program:**

```powershell
.\lexer.exe .\program.rice
```
*Expected output:* `Lexical analysis completed successfully. Symbol table written to Symbol Table.` (Exit code 0).

**2. Error-handling test:**

```powershell
.\lexer.exe .\program_error_handling.rice
```
*Expected output:* Displays line/column error diagnostics to stderr; writes output with `INVALID` rows to `Symbol Table` (Exit code 1).

**3. Invalid-token test:**

```powershell
.\lexer.exe .\program_invalid.rice
```
*Expected output:* Displays invalid symbol transition diagnostics to stderr; records errors in `Symbol Table` (Exit code 1).

## 7. Where to make changes

All changes are now located in specific sections of [`lexer.c`](./lexer.c):

| Modification | Location in `lexer.c` |
|---|---|
| **Add a new token kind** | 1. Add enum member to `TokenKind` (Section 1).<br>2. Add entry to `accepting_states[]` (Section 4).<br>3. Add case to `dfa_token_kind_name()` (Section 4). |
| **Add / edit a keyword or reserved word** | 1. Add prefix states to the word enum (Section 4).<br>2. Add transitions in `dfa_step_word()` (Section 4).<br>3. Add initial character dispatch in `dfa_step()` `STATE_START` (Section 4).<br>4. Add accepting entry in `accepting_states[]` (Section 4). |
| **Add / edit an operator or symbol** | 1. Add state enum to `SYMBOL_*` (Section 4).<br>2. Add single-character case to `dfa_step()` `STATE_START` (Section 4).<br>3. Add multi-character compound step in `dfa_step_symbol()` if applicable (Section 4).<br>4. Add entry to `accepting_states[]` (Section 4). |
| **Change identifier validation rules** | Update `is_identifier_start()`, `is_identifier_part()`, `dfa_is_identifier_*()` (Section 2), and the identifier scanning block in `lexer_scan()` (Section 5). |
| **Change numeric literal format** | Update the `CLASS_DIGIT` scanning block in `lexer_scan()` (Section 5). |
| **Change string, char, or comment rules** | Update the `@`, `'`, or `"` blocks in `lexer_scan()` (Section 5). |
| **Modify source file constraints or encoding** | Update `valid_source_extension()` and `lexer_read_source()` (Section 5). |
| **Modify Symbol Table formatting** | Update `dfa_write_symbol_span()`, `dfa_write_acceptance_span()` (Section 4), and `main()` (Section 6). |
